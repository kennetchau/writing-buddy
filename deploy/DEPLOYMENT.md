# Deployment Guide — Fedora host, podman quadlet

Deploys **two new containers** (`novel-db` + `novel-app`) on a shared podman
network. The existing **llama.cpp container is never touched** — the app
talks to it only via its HTTP API.

Everything lives in this repo:

```
deploy/
  Dockerfile                 # multi-stage: node:22 build (tsc + esbuild bundle of /js/story.js) → runtime
  install-quadlet.sh         # one-shot installer (idempotent)
  quadlet/
    novel.network            # shared podman bridge "novel"
    novel-db.container       # postgres:16, named volume, network-only
    novel-app.container      # the app, host port 9187, named image volume
    novel-backup.service/.timer   # nightly pg_dump + images (14× retention)
    novel.env                # documentation of intended values
scripts/backup.sh            # the backup job (installed by the script)
```

> **Why quadlet, and the quirks:** the old build (Base OS) ran its whole
> stack this way on this host and hit several rootless-podman/pasta/SELinux
> pitfalls. Hard lessons already baked into the units below:
> - the quadlet generator does **no `${VAR}` expansion** and rejects
>   `ExtraHosts` — all values in the unit files are hard-coded;
> - reach llama via **`host.containers.internal:21000`** (the stable podman
>   host name) — NOT the pasta netns IP (e.g. 10.2.0.2), which churns;
> - use **named volumes** for all data (podman initializes ownership from
>   the image uid) — this app has no bind mounts, so no `:z`/chown dance
>   is needed at all (a deliberate simplification vs the old build).

## Phase 0 — Pre-flight (~5 min)

```bash
# 1) ports: 9187 must be FREE; 21000 must be TAKEN by llama.cpp
ss -ltnup | grep -E ':(9187|21000)\b'
#    (if 9187 collides with something else, check the old build's
#     plan/reference/usedport and change PublishPort in
#     deploy/quadlet/novel-app.container before installing.)

# 2) llama.cpp is up and serving its router API on host port 21000
curl -s http://127.0.0.1:21000/v1/models | head -c 200

# 3) tooling
podman --version          # quadlet support = Fedora default
loginctl enable-linger "$USER"   # REQUIRED: user units keep running
                                # when your session is closed (backups!)

# 4) get the repo at a STABLE path (install script + backups don't move it)
sudo mkdir -p /srv/novel && sudo chown "$USER" /srv/novel
git clone <repo-url> /srv/novel/repo     # or rsync this checkout
cd /srv/novel/repo
```

## Phase 1 — Install (~3 min)

```bash
deploy/install-quadlet.sh
```

What it does (idempotent — re-run after every `git pull`):

1. `podman build -f deploy/Dockerfile -t novel-app:latest .`
2. copies the three quadlet units into `~/.config/containers/systemd/`,
   **generating a fresh `SESSION_SECRET`** into `novel-app.container`.
3. copies `scripts/backup.sh` → `~/.config/systemd/user/backup-novel.sh`
   and installs `novel-backup.service` + `novel-backup.timer` (nightly
   03:30 UTC, 14× retention into `/srv/novel/backups/`).
4. `systemctl --user daemon-reload`, **creates the `novel` CNI network via
   `podman network create`** (idempotent — `podman network exists` guard;
   the `.network` quadlet unit is NOT used because the deploy host's podman
   generator doesn't surface `.network` files to user systemd), then starts
   `novel-db`, `novel-app`, enables the backup timer.

> **Quadlet units are generated at every session start** — they are
> *started*, never enabled (the podman generator recreates them; same as
> the old build's units). The backup units are plain user units and are
> enabled properly.

### First-boot config

Two values you must check in
`~/.config/containers/systemd/novel-app.container` **before the first
successful boot** (the installer warns if it finds the placeholders):

| Env | Change to |
|---|---|
| `ADMIN_PASSWORD` | the initial admin password (bootstrap only fires while the user table is empty) |
| `ADMIN_USERNAME` | default `admin` (leave as is) |

`SESSION_SECRET` is already generated by the installer. If you edited the
unit after the first boot: `systemctl --user daemon-reload && systemctl --user restart novel-app`.

## Phase 2 — Verify (~2 min)

```bash
systemctl --user status --no-pager novel-db.service novel-app.service novel-backup.timer
curl -s http://127.0.0.1:9187/api/health
# → {"ok":true}
journalctl --user -u novel-app.service -n 40 --no-pager
# expect: schema applied, "[auth] created initial admin user \"admin\"",
#         "listening on :9187". If the DB was still initializing, you'll
#         see the retry lines — that's expected and self-healing.
```

Then in a browser: `http://<host>:9187/` → log in as the admin → **reset
the admin password immediately** (⚙ Admin → Users → Reset pw) and change
`ADMIN_PASSWORD` in the unit to something meaningless so nobody can
re-bootstrap it.

### Llama check (from the AI Monitor page)

Open **AI Monitor** → the Model card should list the model as
`unloaded` (reachable). Click **Load**, wait, and the status flips to
`loaded` (polling every 5 s). If it shows *model server unreachable*:
llama.cpp is down, or `LLAMA_URL` is wrong — fix is a one-line edit of
`LLAMA_URL` in the unit + daemon-reload + restart. (App boots and writing
works fine even when llama is down — only the AI buttons fail.)

## Phase 3 — Smoke (end-to-end, ~5 min)

```bash
bash testing/smoke.sh http://127.0.0.1:9187 admin '<admin-password>'
# → "== smoke result: 27 passed, 0 failed"
```

Covers login → universe → lore → image upload → story → verify → chapters
→ finalize → shelf → AI Monitor (shape) → admin add/delete → logout. AI
generation itself needs the real model; do one manual **Generate** on the
Story page with the model loaded and confirm the stream renders live and
the draft chapter lands in the list (the model is slow — minutes for a
chapter is normal, and the navbar badge tracks it everywhere).

## Phase 4 — Backups (NFR-05)

`novel-backup.timer` runs `scripts/backup.sh` nightly at 03:30 UTC (+
boot catch-up): `pg_dump` **inside** `novel-db` plus a tar of the
`novel-images` volume into `/srv/novel/backups/<YYYYMMDD>/`, keeping the
newest 14.

```bash
systemctl --user status --no-pager novel-backup.timer
systemctl --user start novel-backup.service        # run now
ls -lt /srv/novel/backups/
```

**Restore drill:**

```bash
# 1) database (the dump is crash-consistent; from the host, exec into the db)
podman exec -i novel-db psql -U novel novel \
    < /srv/novel/backups/<date>/novel.sql

# 2) images back into the named volume (the tar was made of the volume root)
podman run --rm -v novel-images:/d docker.io/library/alpine:3 \
    sh -c 'tar -xzf - -C /d' \
    < /srv/novel/backups/<date>/images.tar.gz

# 3) confirm
curl -s http://127.0.0.1:9187/api/health
# log in; stories/lore/images are back as of the backup timestamp.
```

## Operations quick-ref

| Task | Command |
|---|---|
| Update the app | `cd /srv/novel/repo && git pull && deploy/install-quadlet.sh` (rebuilds image; units + DB schema are additive/idempotent) |
| Logs | `journalctl --user -u novel-app.service -f` |
| Restart app | `systemctl --user restart novel-app.service` |
| Emergency stop | `systemctl --user stop novel-app.service` (data safe: named volumes + nightly backups) |
| Check model | AI Monitor page, or `curl -s http://127.0.0.1:9187/api/model` (needs a cookie in a real client) |
| Add a user | ⚙ Admin → Users (temp password; the user logs in and uses it) |

## Troubleshooting

| Symptom | Fix |
|---|---|
| `novel-app` restart-loops, log shows `database init failed (attempt x/10)` | `novel-db` is unhealthy: `podman logs novel-db \| tail`; check `novel-pgdata` exists (`podman volume ls`). The app retries 10× then gives up — once the DB is fixed, `systemctl --user restart novel-app`. |
| AI Monitor: *model server unreachable* | llama.cpp down, or `LLAMA_URL` stale. `curl -s http://host.containers.internal:21000/v1/models` from inside the app container (its name is `systemd-novel-app` — quadlet names containers after the unit when `ContainerName=` is unset): `podman exec -it systemd-novel-app node -e "fetch('http://host.containers.internal:21000/v1/models').then(r=>r.text()).then(console.log)"`. If it fails from inside but works on the host, update `LLAMA_URL` in the unit (daemon-reload + restart). |
| Unit "won't start" after editing | `journalctl --user -u novel-app.service --no-pager \| tail -40` — usually a typo in a hard-coded `Environment=` line (the generator does no expansion; quote values that contain spaces). |
| `Error: unable to find network with name or ID novel` | the CNI network doesn't exist / wasn't created before the containers started. `podman network exists novel \|\| podman network create --subnet=10.91.0.0/24 --gateway=10.91.0.1 novel`, then `systemctl --user restart novel-db`. (The `novel.network` quadlet file + CLI both converge: `podman network create` no-ops if the unit already made it.) |
| `Failed to start novel.network.service: Unit novel.network.service not found` | your podman version's quadlet generator doesn't surface `.network` files to user systemd (the `.container` units still generate fine). Harmless — create the network with the CLI command above; re-running `deploy/install-quadlet.sh` detects this automatically. |
| Port 9187 collision at install time | change `PublishPort=` in `novel-app.container`, daemon-reload, restart. |
| App logs `listening on :9187` but host `curl 127.0.0.1:9187` is refused | `podman port systemd-novel-app` showed host port ≠ 9187 (this host's podman: a bare one-number `PublishPort=9187` lands as container-9187 → random host port, e.g. `{0.0.0.0 33811}`). Fix: `PublishPort=9187:9187` (two numbers, as in the unit), `systemctl --user daemon-reload && systemctl --user restart novel-app`. Diagnostics: `deploy/diag-port.sh`. |
| Admin password forgotten | the `ADMIN_PASSWORD` env only applies when the user table is **empty**. With data present: stop the app, `podman exec -it novel-db psql -U novel -c "UPDATE \"user\" SET pw_hash='<argon2id hash>' WHERE username='admin'"` — generate a hash with `node -e "import('@node-rs/argon2').then(async a=>console.log(await a.hash('newpw')))"`. |
| SELinux denials in the journal (`avc: denied`) | shouldn't happen (no bind mounts — only named volumes, which podman labels itself). If you add a bind mount later, append `:z` to its `Volume=` line. |

## Tearing it down (rare)

```bash
systemctl --user stop novel-app.service novel-db.service
systemctl --user disable --now novel-backup.timer
podman network rm novel   # (only when you also remove the containers above)
systemctl --user daemon-reload          # drops the generated units
podman volume rm novel-pgdata novel-images   # DESTROYS ALL DATA
rm ~/.config/containers/systemd/novel.* ~/.config/systemd/user/novel-backup.* \
   ~/.config/systemd/user/backup-novel.sh
```
